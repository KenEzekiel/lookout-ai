# F-AUTH-ACCESS: Operator identity and device pairing

Status: partial

Depends on: none

## Behavior

The account-mode prompt centers its label and inline action with an explicit 8-pixel horizontal gap and shared vertical alignment. Both sign-in and registration prompts wrap between the label and action on narrow screens. This spacing fix is introduced by the current PR in [the account screen](../../../apps/app/src/components/access/account.tsx); authentication behavior is unchanged.

Account, onboarding, pairing, invitation, retry, and removal controls use the shared action icons and size variants described by F-APP-SHELL. Live view and Remove access use the same compact size within each device row; dialogs retain visible labels and confirmation boundaries.

Devices and Team use list skeletons until their first read completes. Account, onboarding, pairing, invitations, access removal, sign-out, retries, and configuration refresh use shared busy buttons with specific pending labels and duplicate-submit protection. Forms reserve label width and retain values on failure.

People register with email/password and immediately create or join one workspace. Verification email and password recovery are deferred. The creator is its owner. Invitation links and six-digit codes admit one signed-in operator within 15 minutes. Owners remove operators and authorize or revoke devices. Operators do not manage access.

Monitoring browsers display a five-minute pairing code. The owner approves it in a separate session or switches their current browser directly into restricted device mode. Both paths preserve any human login and open capture directly. Devices can access every monitoring source in their workspace for this demo, replacing the original per-source assignment requirement. Device credentials survive refresh and restart while browser storage remains. Revocation blocks the next request. Signing out of a separate owner session leaves the device paired.

The interface separates Team and Devices. Only owners see invitation, pairing, and removal actions. Invitations and device approvals open focused dialogs. Removal requires confirmation; first-time same-browser activation asks for a name and explains that the login is preserved. Signup keeps the password-recovery limitation visible beside the password field. Errors preserve entered values, and failed workspace loads can be retried.

Devices and Team receive workspace-scoped SSE snapshots so pairing, revocation, and membership changes from another browser appear without a page reload. Owners and operators can use **Refresh** to request the latest list immediately. Refresh shows a disabled pending control, preserves the last list on a failed request, and offers retry. Interrupted live updates show a visible refresh fallback. Authorization badges still describe pairing access, not capture health.

Access dialogs and action buttons use the shared interaction motion styles. Pending labels and new validation feedback use a short opacity reveal while retaining the existing disabled state, field retention, and accessible feedback. Reduced motion presents these changes immediately.

The Devices screen places the owner-only **Use this device instead** action in a labeled **This browser** secondary card beside connected devices on wide screens and after them on narrow screens. It identifies the current workspace-management role and resumes a valid saved pairing, or opens the first-time name dialog. Connected-device rows group each name with its authorization badge, a prominent **Live view** action, and the owner-only secondary **Remove access** control. Revoked rows have no viewing action. Owners can also reconnect active or revoked device rows through a fresh pairing code.

Returning to the workspace sets a browser preference without removing its HttpOnly device credential. Signed-in users return to management; standalone browsers return to sign-in and can resume the remembered device without entering account credentials. **Forget this device** confirms and clears local pairing only. Workspace revocation remains an owner action. Capture resources stop when leaving the station. Successful account sign-in and registration retain the saved device cookie; a different or unassigned account cannot use it until membership matches. Browser storage loss still requires pairing approval.

**Reconnect** keeps the selected device ID, name, and history. An owner enters a fresh code from the replacement browser. One D1 batch rotates the device token, restores revoked access when explicitly requested, and consumes the unexpired pairing request. The previous credential and any old unclaimed pairing request no longer authorize capture, configuration, reports, evidence, or signaling. Operators and foreign workspace owners cannot reconnect it. A signed-in replacement browser must belong to the paired workspace. Device cookies alone never authorize human actions.

## Entry points

Open `/` (redirects to `/devices`) for registration, sign-in, create-or-join onboarding, and workspace access controls. `/join?token=...` preserves an invitation through signup and opens the join action directly instead of showing a competing workspace-creation form. Successful onboarding replaces the invitation URL with the Devices destination so used invitations are not offered again after membership removal. A secondary action accepts an invitation code or returns to workspace creation. `/monitor` pairs a browser without entering the owner's password. Devices offers **Add device** for a code displayed on another device. The shared member header offers **Switch to device mode** on every workspace page. Owners enter a name only for first-time setup. A remembered same-workspace device opens `/device` without creating another record. Operators open `/monitor`, generate a code, and ask an owner to approve it from another browser. **Back to workspace** leaves pairing without signing out; approval followed by a successful claim opens `/device` without ending the human session. The paired screen links to the capture station and distinguishes local capture from unimplemented AI assessment. Revoked devices display the failure and can return to sign-in.

## Wiring and compatibility

The shared workspace layout preserves principal state and its five-second access check across `/devices`, `/team`, `/triggers`, and incident routes. Sign-out, onboarding completion, revoked access, and retry still use the same handlers. Successful onboarding replaces the invitation URL with `/devices`. The current PR changes navigation ownership and paths without changing authentication or workspace permissions.

Better Auth owns accounts and human sessions. D1 owns application workspace membership, invitations, devices, and pending pairing. `principal` resolves a live human session first, then standalone device access unless the browser has chosen workspace/sign-in mode. `/device` explicitly requests `principal?mode=device`, which checks and renews the device cookie independently. `member` protects human handlers and its owner check protects administration. `monitoringDevice` protects device handlers. Consumers derive workspace scope from these identities and include it in resource queries.

`GET /api/access/team/events` authenticates members before opening an SSE response and before each five-second D1 snapshot. It sends the existing `teamSchema` shape only when it changes, with comment heartbeats otherwise. Streams close after five polls to bound per-request database work; native EventSource reconnects after three seconds and receives a complete snapshot, so replay IDs and in-memory cross-Worker broadcasters are unnecessary. Removing membership or ending the human session ends the stream on its next access check and clears the displayed list. Devices, visitors, and unassigned accounts cannot open the stream. Leaving the workspace screen closes its EventSource. Existing JSON team reads, administration permissions, pairing cookies, and capture/signaling protocols remain unchanged. The browser QA server forwards response chunks immediately rather than buffering the SSE body.

All existing access and configuration handlers use this boundary. F-RULE-CONFIG enforces member writes, device reads, workspace isolation, and revocation. Removing an operator atomically disables and version-bumps rules naming that recipient. The local capture route requires a device principal, carries its workspace and device IDs in local samples and video handles, and stops on revocation when the principal check fails. F-AI-RELAY uses the device principal and workspace-scoped enabled rule versions, with real endpoint coverage in [relay tests](../../../apps/app/tests/api/assessment.test.ts). F-INCIDENT-RESPONSE uses the same principals for device sessions and reports, member inbox/detail reads, and versioned response commands. Its real-handler tests cover workspace isolation, removed members, and revoked devices. F-ALERT-INAPP uses the member boundary for recipient-filtered delivery reads; its real-handler tests deny devices, removed members, and foreign workspaces. F-SOURCE-PEER uses current member/device principals on every signaling request and restricts session offers, answers, and polling to their participants and workspace. It ends live viewing on revocation or membership loss through polling and expiring leases. F-ALERT-PUSH binds subscriptions to live human sessions and workspace membership in [the push service](../../../apps/app/src/server/push.ts). Sign-out invalidates that session; switching to capture preserves it and its push eligibility; delivery rechecks session expiry and current membership. Member removal deletes workspace subscriptions in the same D1 batch. [Push endpoint integration tests](../../../apps/app/tests/api/push.test.ts) cover visitor and device denial, session ownership, sign-out, expiry, and removed members. F-EVIDENCE-REPLAY validates the current paired device against the incident's workspace, device, session, and event identity on writes, and checks current membership on every replay request. Its real-handler tests cover cross-workspace and removed-member denial. Live capture-to-report submission and MCP remain unconnected. These gaps keep this record partial; a paired screen alone is not evidence of active monitoring.

F-DEVICE-HEALTH reuses `monitoringDevice` for metadata reports and `member` for workspace health reads. Device and workspace identity come from the authenticated principal. Writes also check revocation in SQL, and operator reads scope device/source/rule data to that workspace. Existing pairing and source-access permissions remain unchanged.

## Decisions and sources

The current PR follows the user-approved HTML UI study and the instruction to keep trigger descriptions plain. The Devices register now uses full-width divided rows and places browser activation below the paired-device list. Live view uses the shared outline Button, while removal, pairing, permissions, health reports and activation confirmation keep their existing behavior. Source: [UI implementation](../../../apps/app/src/components/access/workspace.tsx). Existing integration journeys remain regression coverage; manual browser evidence is recorded in the PR.

[Issue #103](https://github.com/KenEzekiel/lookout-ai/issues/103) and the user's approval replace forced sign-out and credential deletion on return. Synthesis decision: keep account identity and device authorization independent at their existing server boundary, rather than make membership grant capture access. Model the Domain keeps one device identity across navigation and reconnection. Retain restricted standalone authorization, owner-only provisioning, workspace scoping, and revocation. The existing integration suites cover retained sessions, duplicate-free resume, forget, credential rotation, reconnect recovery, and consumer permission boundaries. Current browser and verification results belong in the implementation PR.

This PR follows Aji's request to update the device list when a new device connects, add SSE, and expose manual refresh. Synthesis decision: reuse `teamSchema` and current D1 authorization rather than introduce another durable service or rely on an isolate-local subscriber registry. Model the Domain keeps both transports on one parsed snapshot; Fix Root Causes adds a subscription to the screen that previously refreshed only after its own actions. Server-side five-second reads trade database traffic for a small demo implementation. This does not implement F-DEVICE-HEALTH heartbeats or change F-SOURCE-PEER signaling. [Cloudflare streaming guidance](https://developers.cloudflare.com/workers/runtime-apis/streams/) and [per-request limits](https://developers.cloudflare.com/workers/platform/limits/) informed the bounded stream lifetime. Deployment verification remains outside this change.

[Issue #86](https://github.com/KenEzekiel/lookout-ai/issues/86) requests a discoverable operator-to-device switch. Synthesis decision: add a persistent header action and route operators through existing owner-approved pairing. The owner-only browser-card shortcut from [PR #84](https://github.com/KenEzekiel/lookout-ai/pull/84) remains available. Both owner entry points reuse the existing confirmation dialog and activation endpoint. The current PR implements this decision using the schema-derived member role and shared button styles without changing session or authorization boundaries.
